Summary

Microservices vs Monolith Architecture
The instructor discussed the differences between monolith and microservice architectures, explaining that microservices involve independent services communicating through APIs or Kafka events, which can be scaled and updated independently without affecting the entire system. They highlighted that microservices allow for easier scaling, better fault tolerance (as downtime in one service doesn't affect others), and the ability to use different databases based on service needs, while also noting that microservices can be more complex to manage and may require more resources than monolithic architectures.


Microservices vs Monolithic Architecture
The discussion focused on the trade-offs between monolithic and microservice architectures, with GeeksforGeeks explaining how microservices can increase response times due to network calls between services, while Theja mentioned banking applications as examples where monolithic architecture is still preferred for speed. The group then discussed building an e-wallet application using microservices, with GeeksforGeeks outlining assumptions including single-user wallets and wallet-to-wallet transfers, with all services running on localhost using different ports to simulate a distributed environment.


Microservices Architecture and Setup
The team discussed the architecture of a microservices-based system, including user, wallet, and transaction services. They agreed on the need for a notification service and an authorization service. GeeksforGeeks demonstrated setting up a new project in IntelliJ using Maven and various dependencies, including Spring Boot, Kafka, and Spring Security. They discussed two approaches to organizing the code: using separate repositories for each service or using a monorepo structure with different modules.


Microservices Deployment with AWS Lambda
The discussion focused on building and deploying microservices using AWS Lambda and serverless functions, with each service having its own serverless.yml file and configuration. The team explained how to add Maven modules to a project, with each module having its own pom.xml file and being able to communicate with other services running on different ports (8080, 4000, and 6000 in this example) when running locally. They clarified that while service registry and API gateway are needed for cloud deployment, these are not required for local development, and communication between services can be handled through direct API calls or Kafka events.


Port Allocation and Maven Dependencies
The discussion focused on two main topics: port allocation for applications and Maven dependency management. GeeksforGeeks explained how to select available ports for running applications, demonstrating the process of changing from port 4000 to 5001 due to conflicts. The conversation then shifted to Maven dependencies, where GeeksforGeeks illustrated how a parent project can inherit and share dependencies with child modules, showing that even though the wallet service's pom.xml file doesn't explicitly define Spring Security, it can still access it through the parent project's dependencies.


Database Configuration for Service Scalability
GeeksforGeeks explained the importance of configuring different databases for different services to prevent a single point of failure and distribute the load. They discussed how running multiple databases on the same server can lead to performance issues, and recommended hosting databases on separate servers to improve scalability and reliability. Anuradha asked about sharing the same database between different services, to which GeeksforGeeks clarified that while the host remains the same, different databases can be used to avoid bottlenecks.
